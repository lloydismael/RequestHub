# Unreleased: Code-scanning hardening

Status: local validation only. No release version, release date, integrated change revision, or publication is assigned here.

## Changes

- **Sign-in and profile:** The application and Django admin use the same PostgreSQL-backed login quotas before password checks: 30 attempts per client source, five per account and source, and five per existing account across sources in a 15-minute window. Unknown accounts use the source limit; generic feedback and dummy verification avoid disclosing account state. Success clears only completed failures for that account and source; denied attempts do not extend a window, and a quota-storage failure does not allow unchecked authentication. Existing aliases, staff checks, redirects, and proxy resolution are preserved. Accounts flagged for a password change must set a different password before accessing protected pages, including admin. Only the Request Hub Admin role can change their own department.
- **Configuration and migration:** `request_hub/settings.py` uses the custom Django admin app config to select the shared login form without replacing registered models or admin URLs. Apply additive `accounts` migration `0030_loginthrottlebucket` before enabling the sign-in changes; it creates keyed quota rows with indexed expiry and bounded cleanup. No new environment variables, dependencies, or SQR/request schema changes. No live migration was performed. Keep `TRUSTED_PROXY_CIDRS` limited to controlled peers; plan to monitor shared-source and account quota denials in a controlled rollout.
- **SQR approval and tracker:** Admin or the assigned PM-ESG reviewer controls review, protected quote, proposal, and revenue actions. Approved quote fields stay read-only in Classic, the unified tracker, and the submission editor until a reviewer explicitly selects **For Revision**. The same policy governs Save, Undo, and History Restore; reopening clears approval metadata, and reverting a later edit cannot silently reopen a quote or attach incompatible approval history. Existing access to allowed remarks, applicable configured answers, approvals and related email choices, valid Undo, and independently authorized Delivery work is retained. Classic PM and SSE names remain literal after Save and Undo; unassigned cells keep the en dash. The unified tracker asset version was bumped for the changed controls.
- **Request management and recovery:** Removal by confirmation or the scoped DELETE handler is idempotent and preserves the record, status history, and activity for single or bulk Admin recovery. The confirmation explains recovery. Collaborative activity edits share the same request/role check when opening and submitting the editor. New engineer entries credit the actor (including backup engineers); existing authors and authorized admin attribution are preserved. Eligible engineers see the stored account and recorded request date as read-only; the separate Deployment scheduling controls remain editable. Configured answers use saved read-only values, and the manager form displays form-wide validation errors.
- **Tests and maintenance:** Added policy coverage for login quotas, concurrency, password and department rules, reviewer permissions and approval transitions, Undo/Restore and assignment labels after Save and Undo, request removal/recovery, collaborative activity, and configured forms. Mobile and seasonal tests now share standard-library script extraction/omission for trusted local fixtures only; it is not an application sanitizer. The SQR refresh fixture also uses this parser for case-insensitive script tags and spaced closing tags, while retaining only inline JSON data. The mobile fixture retains inert inline chart JSON only when it opts into local scripts. The PPT keyboard check explicitly enables Classic just for that fixture. Existing CSV/XLSX literal text and numeric-cell safeguards were rechecked; export code was not changed. README documents the rules, rollout order, and verification limits.

## Follow-up to the refreshed scan

- **Privileged accounts ([#84](https://github.com/lloydismael/RequestHub/security/code-scanning/84)):** Request Hub Admins can still manage ordinary accounts, but cannot reset credentials, edit, or delete Django staff and superuser accounts. The dedicated editor and legacy bulk form enforce the same rule. Protected accounts stay listed without management actions for these admins. Existing protection against deleting Django superusers remains.
- **SQR retention ([#88](https://github.com/lloydismael/RequestHub/security/code-scanning/88)):** Only Django superusers may permanently delete protected records, including through Classic, the unified tracker, bulk replacement, and Django admin. Protection covers approval, closure, billing, and qualifying history even after reopening; blank or null historical dates do not protect otherwise unprotected drafts. Django staff cannot edit the protection fields or change/delete protected history through Django admin. Recovery Center rejects a non-superuser restore if it would remove protected SQRs, their protection, or their history. Owners retain permitted draft deletion. Tracker controls reflect the server rules.
- **Request authorization ([#86](https://github.com/lloydismael/RequestHub/security/code-scanning/86)):** Historical SQR ownership preserves request visibility and the ability to edit one's own SQR, not permission to edit the request, change its status, or post activity. The UI shows when the request is read-only and omits write controls. Existing assignment, activity ownership, and primary-only status rules remain. Collaborative assignment email is sent after the update commits.
- **Request update consistency ([#85](https://github.com/lloydismael/RequestHub/security/code-scanning/85)):** A requestor edit, the primary and backup assignment comparison, and their lifecycle updates share a transaction. A lifecycle write failure rolls back the edit.
- **Idle expiration ([#87](https://github.com/lloydismael/RequestHub/security/code-scanning/87)):** Django enforces the six-minute idle deadline for enabled accounts, using a separate deadline tied to the Django session. Request Hub and Django admin share the five-minute warning and renew on deliberate activity or confirmation; background polling and audit-only heartbeats do not renew. Each tab checks the current deadline without navigating away from unsaved work while the session is live. The opt-out and manual sign-out remain, and idle expiry retains its session-audit reason.
- **Tests, configuration, and documentation:** Added Django and Node regressions for the five changes. Apply additive `accounts` migration `0031_sessionidledeadline` before enabling the idle middleware. The deadline record is removed with its Django session; activity does not refresh Django's separate session expiry. No new environment variables or dependencies. The README describes permissions and idle behavior. Proxy trust ([#58](https://github.com/lloydismael/RequestHub/security/code-scanning/58)) still requires checking the deployed peer allowlist and forwarding chain; no live configuration changed.
